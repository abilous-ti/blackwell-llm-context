# Prospective replication with randomized blocks: protocol

**Status: DRAFT.** `freeze.py` freezes the protocol. It refuses to freeze without concrete window
boundaries, interruption rules, a schedule within the call budget and its retry headroom, committed
code, or if records already exist. It sets `status`, `frozen_at_utc` and `harness_commit` in
`design.json`, writes `schedule.jsonl`, and writes `FREEZE.json` with the SHA-256 of the design, of
the schedule and of every code file the collection and the analysis run. `run_replication.py`
refuses a live window, and `analyze.py` refuses a final status, unless `freeze.verify` reports no
problem: a changed model identifier, level, schedule or code file, or missing freeze metadata, stops
both. Any change after freezing is logged in `DEVIATIONS.md` beside the records, with date and reason.

## 1. Purpose

The published measurements were collected condition by condition: the driver ran every draw of one
condition–task cell before the next, arm by arm (`harness/measure_blackwell.py`, `measure()`), so
condition and collection time are associated. Within a cell the draws were sent one after another or
concurrently, according to the driver's `--workers` option (default 1), whose value was not
recorded; concurrency in the original runs is therefore not established. This replication
re-measures the central effects with every compared condition requested throughout every collection
window, in randomized blocks. It is a prospective confirmation of previously identified effects, not
a search for new ones: the tasks, contexts and contrasts are those of the published record.

**Deviation (deliberate).** The published grader ran model-generated code with the parent
environment, including provider keys. The replication runs it in the current harness's
credential-stripped environment. The checks are unchanged.

Requested models: `claude-haiku-4-5`, `claude-sonnet-4-6`, `claude-opus-4-8`, `gpt-5.5`,
`DeepSeek-V4-Pro`, `Kimi-K2.6`. Each request sends the model name, one user message and an output
limit of 8000 tokens; temperature, top-p, system prompt and sampling seed are not set, as in the
published runs. Each model's endpoint and key come from its own environment variables
(`BW_ENDPOINT_*`, `BW_KEY_*`; there is no shared fallback). The endpoint is recorded as its provider
domain with the resource name replaced by a short hash, never with the key; any provider-side
configuration change is logged as a deviation.

## 3. Design

| Task | Conditions | Purpose |
|---|---|---|
| `api_post_ok` | W1, W2, W1plus | API-side advantage (A1) and superset harm (H1) |
| `enc_amount` | W1, W2 | opposite advantage (A2), needed for PASS incomparability |
| `api_argorder` | none, W1, W1plus | second harm contrast (H2) and the no-context baseline |

A **block** is one request per condition of one task for one model, in a random order, requested back
to back. Within a window, each model receives `blocks_per_window` blocks per task, and the blocks of
the three tasks are interleaved in a random order. The complete schedule is generated by
`make_schedule.py` from `scheduler_seed` (unrelated to model sampling, which uses no seed) and frozen
with its hash before any request.

**Windows:** six windows of five hours, Europe/Kyiv (UTC+03:00): Thursday 1 October 16:00–21:00;
Friday 2 and Saturday 3 October 10:00–15:00 and 16:00–21:00; Sunday 4 October 10:00–15:00. Each
window is stored with its start and end as ISO 8601 times with the offset; windows may not overlap. *Deviation (2 October 2026):* d2-pm, missed with no request issued, had its end extended from 21:00 to midnight; see `results/replication/DEVIATIONS.md`.

**Concurrency.** Each model has at most `max_in_flight_per_model` = 2 requests in flight: lane *j*
takes the blocks whose position in the window is *j* modulo 2, so a block's requests stay back to
back and every request records its lane. The six models run in parallel. At 40 blocks per window a
model receives 320 requests per window. The retained re-measurements give Kimi-K2.6, the slowest
model, a mean of about 2,550 output tokens per request (median 1,747, maximum 8,000): one lane would
need about 45 tokens/s sustained to finish in five hours, two lanes about 23. The other models need
at most 20 (one lane). The number of lanes is fixed before freezing, never changed during collection.

## 4. Sample size and budget

**Design: 40 blocks per window**, i.e. 6 windows × 6 models × 8 conditions × 40 blocks = 11,520
requests, n = 240 blocks per condition. The call budget is 12,288 calls, counting every attempt,
retries included, across all windows; the schedule must leave at least 5% for retries, and 11,520
requests leave 768 calls (6.25%). (An earlier ceiling of 8,192 calls allowed at most 27 blocks per
window.)

`power_sim.py` simulates the design, including common and condition-specific drift between windows
and the loss of one whole window, and applies the primary decision rule below. The binding case is
the weakest harm cell of the published record (DeepSeek `api_argorder`, 0.675 to 0.05), tested
against the 0.30 margin:

| Blocks per window | n | Requests | Stable | Common drift | Divergent drift | Divergent, one window lost |
|---|---|---|---|---|---|---|
| 27 | 162 | 7,776 | 0.89 | 0.75 | 0.69 | 0.52 |
| 32 | 192 | 9,216 | 0.97 | 0.88 | 0.84 | 0.69 |
| **40 (chosen)** | **240** | **11,520** | **1.00** | **0.96** | **0.93** | **0.85** |

Every other observed cell reaches at least 0.99 at 40 blocks per window, one lost window included.
Margin claims for effects much smaller than those observed (a harm of about −0.5) remain
underpowered at any affordable n; their any-harm claims are not.

## 5. Records

`run_replication.py` appends to one file per window, one JSON line per event, flushed and fsynced
before the next step (`records.py` lists the types):

- `issued`, before the first attempt of a request: schedule id, lane, actual order, time;
- `receipt`, as soon as the response or an exhausted transport failure arrives and **before any
  grading**: the schedule row, actual order, request start and end (UTC), every attempt with its HTTP
  status and error, requested model, returned model field, response id, usage, stop reason, the
  whole response envelope (with the reply text, stored once, replaced by a marker, so provider
  extras such as a backend fingerprint are kept), endpoint as recorded, prompt hash and raw reply;
- `grade`: extracted code and PASS under both graders;
- `run_start` for every run segment: harness commit, design and schedule hashes, scheduler seed, the
  absence of a sampling seed, Python version, platform, endpoint hosts, calls used so far;
- `window_end` (every request of the window issued), `window_closed` (the end time passed or the budget
  ran out, with the requests not collected), `window_incomplete` (a worker failed).

**Retries.** Only technical failures are retried, with the published client's rule: at most three
attempts, 2 s and 4 s apart, on any exception from the request or from parsing its JSON. A parsed
response is never retried, whatever it contains: refusals, empty text and wrong answers are observed
outcomes. A request whose attempts are exhausted is a missing observation ('failed').

**Live plumbing check.** Before freezing, `smoke.py` runs one short window on one model (Haiku 4.5,
16 requests by default) through the real transport, with its own design copy, freeze and budget,
and writes to `results/replication/smoke/`. It checks the pipeline, not the effects: it never
enters the analysis, and it is reported as a pilot with the date and number of requests.
Pilot record: twelve runs on 30 September and 1 October 2026, 188 calls in all (16 requests per
run on each of the six models; one GPT-5.5 run halted after 12 calls because its endpoint pointed
at the chat-completions API; after the fix both GPT-5.5 runs passed). Every other run passed.

## 6. Interruption rules and budget

1. A window's requests are issued only from its start to its end; no request is issued at or after
   the end (the retries of a request issued before the end may finish after it), and a run is
   started or resumed only inside its window.
2. Each scheduled request is issued at most once. Its response is saved before it is graded; a saved
   response is graded on resumption and never requested again.
3. A request issued but not saved because the run stopped in flight is 'interrupted', and one whose
   transport attempts are exhausted is 'failed'; both are missing and neither is requested again.
4. Requests not issued by the end of their window are 'not collected'. They are never carried into
   another window; the window is closed with `--close` after its end.
5. Every attempt counts against the global call budget (an interrupted request counts as three).
   Once the budget is spent, no attempt is made in any window, and every remaining window is closed
   with `--close`.
6. A model whose last three requests all failed in transport is halted for the rest of the run, so
   a dead endpoint or a wrong key cannot spend the budget. Its failed requests are not requested
   again; the window stays open so the endpoint can be fixed and the window resumed before its end.
   A window lost as a whole (an outage, missing credentials) is closed, reported as missing and not
   replaced.
7. One run at a time per record directory, guarded by a lock file; after a crash the lock is deleted
   by hand once no run is active. A crash can truncate only the last line of a file; the next run
   keeps that partial line as data and the request counts as interrupted.
8. The analysis is final only when every planned window is closed, nothing is pending or ungraded,
   the records match the schedule and the design, and the freeze holds. Until then every result is
   provisional.

## 7. Analysis plan

Every scheduled request is reconciled against the frozen schedule and gets one status: graded,
ungraded, failed, interrupted, not collected, or pending (window still open). For each model and
contrast, a complete block gives d = Y_a - Y_b under the primary grader. The estimand is the
**window-averaged effect** over the planned windows.

- **Primary decision rule.** The window-averaged estimate over the windows holding complete blocks,
  with the one-sided Hoeffding bound for independent variables in [-1, 1] weighted for the actual
  window sizes: half-width sqrt(2 ln(1/alpha) Σ_w 1/B_w) / W, for W windows with B_w complete blocks.
  It does not assume identical distribution across blocks or windows, and it reduces to
  sqrt(2 ln(1/alpha) / B) when the windows are equal. Planned windows without complete blocks are
  listed with every result.
- **Family.** 24 one-sided statements (A1, A2, H1, H2 for six models); Bonferroni, alpha = 0.05 / 24.
  PASS incomparability for a model requires both A1 and A2.
- **Any harm versus the margin.** Each harm contrast is tested for H < 0 and for H <= -0.30 at the same
  level. The margin null contains the any-harm null, so the pair adds no multiplicity; both results
  are reported.
- **Worst case (sensitivity).** Every scheduled block of every planned window, each missing outcome
  imputed against the claim (FAIL for the favoured condition, PASS for the other); a window that was
  never collected enters with all of its blocks at the least favourable value.
- **Windows.** The estimate and a 95% Hoeffding half-width for every window; a descriptive chi-square
  test of the window × {-1, 0, 1} table. A non-significant test does not show that the effect was
  stable, and randomization does not establish backend independence.
- **Secondary, never decisive.** The window-stratified normal bound with the conservative
  blocked-design variance (Pashley and Miratrix); Clopper–Pearson on pooled counts, for comparability
  with the published analysis and valid only if each condition's draws form one binomial sample.
- **Other sensitivity.** The current grader; request statuses tabulated by model, window, task and
  condition; calls used against the budget.

## 8. Reporting

The manuscript gains one protocol paragraph, the provenance table of the original records, a results
table (estimate, primary bound and decisions per model and contrast) and the window plot written by
`analyze.py`; a provisional analysis is marked as such in every output and is not reported as a
result. Original and prospective records stay separate (`results/` and `results/replication/`).
Whatever the replication shows is reported, and the paper's claims are revised to match it.
